# yanshi 偃师

日常开发中大家真正在用的 Skill：按任务复杂度编排 Agent，从需求对齐一路做到可验证的交付。

不是理论框架，也不是一套很重的 Workflow。简单任务直接做，复杂任务再加规划、拆分和交叉审查。

## 为什么用

- **轻量**：一个 `SKILL.md`，没有脚本和依赖。每一步都写了「何时跳过」，按需取用。
- **实用**：来自一线日常开发的工作方式，覆盖需求对齐、自测、交叉审查、端到端测试和人工 Review。
- **通用**：不绑定模型，只区分规划者、实现者、审查者三种角色，用哪个模型由你决定。
- **可验证**：端到端测试的预期结果来自业务契约，不把系统返回了什么当作正确答案。

## 工作流一览

| 步骤 | 做什么 | 何时跳过（摘要） |
| --- | --- | --- |
| 0 判断复杂度 | 选一条够轻的路径：简单任务直接实现加自测 | 已有可信判断且范围没变 |
| 1 需求对齐 | 结合材料与代码，通过 Grill 多轮澄清目标、边界、取舍和验收标准 | 目标、边界和验收标准已经明确 |
| 2 方案设计与审查 | 设计方案 → 对抗性审查，不通过则修订方案；审查后将结论统一沉淀到 Spec / CONTEXT.md | 沿用成熟模式，没有新假设要验证 |
| 3 拆分与执行 | 拆成可独立验收的小任务，必要时用 worktree 并行，由主 Agent 集成 | 简单任务直接实现 |
| 4 实现者自测 | 先处理类型检查、测试和业务断言能发现的问题，清理过度设计；多项优化时做消融实验 | 已有覆盖本次变更的有效自测结果 |
| 5 交叉对抗性审查 | 引入其他 Agent 审查，问题统一交回主编码 Agent 修复并重新验证（新会话替代是流程补充） | 任务简单，不需要交叉审查 |
| 6 端到端测试 | 通过浏览器、API 或 CLI 跑真实业务流程，查库表和日志拿证据 | 简单任务；环境或契约缺失时记录未验证的范围 |
| 7 人工 Review | 先看验收标准和测试，再沿业务路径看高风险点 | 本次不需要人工 Review |
| 8 沉淀与做减法 | 从常做的自测路径独立跑通并保留证据开始，沉淀流程或工具，定期删减约束 | 没有可沉淀的流程，也没有要复查的约束 |

每一步的目的、输入、输出和完整的跳过条件见 [SKILL.md](skills/yanshi/SKILL.md)。

## 安装

**Codex**

```bash
mkdir -p ~/.codex/skills
cp -r skills/yanshi ~/.codex/skills/yanshi
```

**其他支持 SKILL.md 的 Agent**

把 `skills/yanshi` 目录放进该 Agent 读取 Skill 的位置即可，具体路径看各自文档。不支持 Skill 的 Agent，可以直接把 `SKILL.md` 的内容作为指令提供给它。

## 用法示例

```text
用 yanshi 做这个需求：订单列表接口增加按状态筛选，附 PRD 链接。
```

```text
这个改动很小，用 yanshi 判断一下复杂度，简单的话直接改并自测。
```

```text
按 yanshi 的第 5 步，对这个分支做一次交叉对抗性审查，问题列出来交给实现者修。
```

```text
按 yanshi 第 6 步跑端到端测试，预期结果以这份接口契约为准，附上查库和日志证据。
```

## 设计原则

- **不写死模型**：只定义规划者、实现者、审查者三种角色。模型更新很快，写死就会过时。
- **可以跳步**：步骤 0–8 是可裁剪路径；先判断复杂度，已有可信判断且范围未变时可沿用，不额外制造文档和审查环节。
- **审查后共享上下文**：需求澄清后先设计方案并做对抗性审查，再定稿 Spec / CONTEXT.md，让后续实现和审查的 Agent 不必重读全部对话。
- **E2E 预期来自业务契约**：这是唯一不可让步的原则。工具提供证据，但不定义什么是正确答案。
- **验证有边界**：代码和测试可能一起误解需求，验收标准仍需人判断；端到端测试只覆盖选定环境和场景。
- **做减法**：定期复查 AGENTS.md 和 Skill 里的约束，包括 yanshi 自己。
- **标明来源**：`SKILL.md` 中标「（推断）」的内容是对原始经验的补充，不是原文规则。

## 命名由来

偃师是《列子·汤问》中的工匠，造出了能歌善舞的机关人。取「指挥 Agent 干活」之意。
