# 按目标实际操作

1. 运行前用自然语言写清最终目标和每个 case 的验收目标。预期来自已确认的业务契约，不能在看到系统返回后倒推正确答案。
2. 从项目已有资料取得启动、测试数据、版本、身份、权限和清理方法。使用可替换的浏览器、API 或 CLI 操作真实业务入口，不要求提前写一整套浏览器脚本。
3. 信息查询核对结果与可见范围；多轮交互核对仍有效的条件；状态修改核对目标对象、状态变化及持久化。只选择当前任务适用的类型。
4. 要验 Web UI 就真正操作页面；API 只能补充证据。成功提示不能单独证明落库，重新通过权威入口或只读数据库读取状态；同一前端缓存不算独立回读。
5. 用日志或 Trace 解释链路与失败，不用链路“成功”替代业务状态。被测产品是 Agent 时，还要按本任务要求检查答案质量。
6. 将目标、实际结果、证据和未验证部分放在一起。没有环境就写没验；有偏差返回主实现者，修复后重新验证并保留原失败。完成约定的清理，残留问题单列。

不要求先写常规测试用例，不代表普遍禁止 AI 写测试；项目的代码层自测继续使用已有方法。

需要比较执行组合时，用 [comparison-template.md](comparison-template.md) 同时报告通过率、耗时和成本。其字段是记录口径，不是已有实验成绩。
