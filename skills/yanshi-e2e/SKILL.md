# 从业务目标到运行证据

输入是最终业务目标和每个 case 的验收目标，不是预先写好的点击脚本。Agent 根据实际状态选择操作路径。

## 1. 固定目标与环境

读取 [goal-template.md](goal-template.md)，在运行前确定身份、输入、预期结果及对应契约。契约相互冲突或缺少决定正确性的规则时，返回受影响目标；只有获得探索授权才运行探索，探索不判正式通过。

读取 [environment-template.md](environment-template.md)，从项目已有文档、脚本或工具配置取得真实入口、启动和清理方法。不能从实际材料取得的信息保留为空；不猜命令、表名或登录身份。写入前确认允许操作的环境、对象与恢复范围。

## 2. 执行业务路径

使用实际可用的浏览器、API 或 CLI 操作，记录关键状态变化。用户验收 Web UI 时，页面路径是目标的一部分；API 只能补充取证，不能替代 UI 通过。

多轮任务保留会影响最终结果的轮次与条件变化；查询任务检查结果与契约要求的可见范围；状态修改记录对象标识、修改前后状态和独立回读。只覆盖本次目标适用的类型。

## 3. 取证并判定

按 [evidence-template.md](evidence-template.md) 逐目标记录预期、观察与证据。

- 预期来自业务契约，不从当前响应、代码行为或历史错误输出反推。
- 成功提示只证明系统显示了成功；持久化目标还要通过新的权威查询读取。同一份前端缓存不是独立证据。
- 数据查询确认状态，日志与 Trace 解释链路。请求完成不等于业务状态正确；对象、身份和运行必须关联得上。
- 最终一致性按契约规定的终态和等待边界判断。没有等待约定时报告缺口，不自行挑一个等待时长证明成功。
- 被测产品本身是 Agent 时，依据本任务契约同时核对答案内容、来源或上下文约束，不以“有回答”代替质量验收。

已证实违约记 `failed`；目标全部有证据支持才记 `passed`；已经尝试但无法完成可靠判断记 `blocked`；计划内未开始记 `not-run`。探索单列 `exploratory`，不混入正式通过率。

## 4. 处理失败与结束

出现失败时读取 [failure-modes.md](failure-modes.md)，返回偏差和定位证据。默认不改代码；获准修复后建立新运行，关联原失败并复验受影响目标。重试、清理和修复都不抹掉原记录。

按约定清理本次数据，单列清理结果与剩余副作用。结尾给出每个目标状态、证据位置和未验证项；结论限于本次版本、环境、身份和数据。

比较两种以上执行组合时，运行前读取 [comparison-template.md](comparison-template.md) 固定统计口径。将已验证稳定的路径沉淀时使用 [sop-template.md](sop-template.md)，不把失败绕行固化成默认操作。
