# 失败模式：先辨别证据错在何处

本表是判定与排查规则，不是已经发生的项目事故清单。

| 观察或错误结论 | 还需区分什么 | 处理 |
|---|---|---|
| 页面提示保存成功，所以已经落库 | 只是提示、前端缓存，还是权威状态已改变 | 用新请求或只读查询回读同一对象；无回读则持久化未验证 |
| API 成功，所以 UI 验收通过 | 是否真的走过用户要求的页面路径 | API 证据单列；没有页面证据不能关闭 UI 目标 |
| 系统返回看起来合理，所以它是正确答案 | 返回是否符合运行前确定的契约 | 回到契约逐条核对；契约缺口不能由返回值补齐 |
| 后台尚未完成就判失败，或无限等待直到成功 | 契约终态、等待边界与当前中间态 | 依约等待和判定；约定缺失则报告判断边界不足 |
| 第二轮正确，最后一轮却丢了条件 | 条件被用户覆盖，还是被 Agent 遗忘 | 对照关键轮次和仍有效的条件，定位首次偏离 |
| 查询为空就算通过 | 真正无匹配、权限不对，还是数据起点错了 | 核对身份、预置输入与查询规则，不临时造预期 |
| 日志显示请求成功，但状态不符合需求 | 传输成功与业务成功是否混淆 | 用对象级状态核对契约，日志用于解释路径 |
| 第二次跑过了，就删除第一次失败 | 数据被前次污染、内部重试，还是修复后新版本 | 保留原失败；记录重置、重试与版本变化 |
| 旧证据仍被用于新版本 | 改动是否影响契约、身份、数据或被测路径 | 重新验证受影响断言；影响不明则保留未验证 |
| 清理失败，却报告任务毫无遗留 | 业务目标与测试环境恢复是否混为一谈 | 单列残留对象与责任，不掩盖副作用 |
| 所有检查通过，所以答案质量也通过 | 是否真的核对了任务要求的内容与依据 | 按答案契约补证据，不能以非空回答代替正确性 |

只能确认现象时，报告“待定位”，不把候选原因写成根因。项目特有的失败模式必须附真实证据后再加入本表。
