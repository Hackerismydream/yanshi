# 自然语言验收目标

模板为。填写业务结果，而不是点击步骤、选择器或传统测试脚本。一个 case 表达一个可解释的验收目标；以下字段可以写成连续自然语言。

## 最终目标

让 <测试身份> 在 <实际业务入口> 完成 <任务>，最终得到 <用户需要的业务结果>。

## 验收依据

- 契约来源与版本：<已确认的需求、规则或用户决定的位置>
- 本次范围：<包含和不包含什么>
- 当前实现与环境：<版本、未提交改动和环境标识>
- 执行上下文：<测试身份、权限、数据起点、必要的会话背景>
- 允许的副作用与恢复方式：<授权范围和清理约定>

## 每个 case 的目标

Case 标识：<case-id>

类型：<信息查询 / 多轮交互 / 状态修改及持久化；选适用类型>

请让 <测试身份> 完成 <业务意图>。按照 <契约条款>，最终应当 <结果与状态>。在这个过程中，<契约要求保持的条件> 应继续成立；<契约禁止的副作用> 不应发生。

怎样认定目标成立：<用自然语言描述需要看到的行为或权威状态，以及依据；有多个独立要求时分别写清>。

计划从哪里取证：<实际可用的页面、响应、回读状态或链路证据；只描述证据需要，不预设观察值>。

仍待确认：<会影响正确性判断的契约缺口；没有则说明无>。

## 使用说明

先确定契约和预期再运行。已有明确契约无需额外审批；草稿中的未确认假设不作为正式正确答案。观察暴露契约需要修改时，先记录原运行和修订依据，再按新版本验收，不追认旧结果通过。「推断」

实际任务只覆盖适用类型。不需要为了凑齐三类而引入不相关写操作，也不需要把操作路线提前固定为脚本。
