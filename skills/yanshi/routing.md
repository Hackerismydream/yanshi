# 路由规则

本文件的分类、状态、优先级和表格是「推断」，不是原文规定的固定关卡。

## 输入与复杂度

接收目标、范围、验收依据、当前代码与改动、已有证据、可用执行能力和授权。已经能从材料或环境读到的事实，先读取，再决定是否提问。

| 判断 | 典型信号 | 可选路径，不是规定顺序 |
|---|---|---|
| 轻量 | 目标清楚、成熟模式、局部影响、无新关键假设 | 实现 → 自测；有效结果可复用 |
| 需要设计 | 方案选择可能改变验收，多模块依赖或新增机制 | 补对齐或方案，再实现 |
| 需要增量推进 | 变更难以一次理解，存在可独立验收的业务切片 | 拆分 → 每个增量实现与验证 → 集成 |
| 需要强化验证 | 权限、状态、并发、重试、一致性、迁移、回滚 | 选择相关自测、E2E、交叉审查和业务验收 |
| 只缺当前一步 | 已有实现、方案或验证结果 | 从缺口进入，不重走上游 |

这些判断可同时成立。风险与不确定性比代码行数更重要；不设固定评分或规模阈值。范围变化后重新判断，范围未变不重复规划。

## 每一步的进入与退出

只有本次选用的步骤才适用下列完成条件；未选或不适用时直接跳过。

| 子 Skill 与委派指令 | 进入条件 | 等效动作与完成/产物 | 跳过或退回 |
|---|---|---|---|
| `Call the Skill tool with "yanshi-align"`。没有 Skill 调用器时，读取同套件的 `../yanshi-align/SKILL.md` 并按其执行。 | 目标、范围或契约有会改变交付的缺口 | 结合材料与代码追问，留下问题、范围、决策和有来源的验收目标 | 已明确则跳过；关键取舍无人确认则停问 |
| `Call the Skill tool with "yanshi-design"`。没有 Skill 调用器时，读取同套件的 `../yanshi-design/SKILL.md` 并按其执行。 | 存在影响实现的方案取舍或核心假设 | 选择最小方案，用反例审查假设，留下决策与验证办法 | 成熟模式则跳过；需求冲突回对齐 |
| `Call the Skill tool with "yanshi-split"`。没有 Skill 调用器时，读取同套件的 `../yanshi-split/SKILL.md` 并按其执行。 | 需要独立验收的小增量或有真实并行机会 | 划定各增量目标、边界、依赖和集成责任 | 简单任务或已有可用拆分则跳过 |
| `Call the Skill tool with "yanshi-implement"`。没有 Skill 调用器时，读取同套件的 `../yanshi-implement/SKILL.md` 并按其执行。 | 当前范围内存在已明确且获准的代码改动 | 实现或修复，返回变更、集成情况和需验证的影响 | 只要求分析、审查或验收时跳过；不清楚怎么才算对则回对齐 |

| `Call the Skill tool with "yanshi-accept"`。没有 Skill 调用器时，读取同套件的 `../yanshi-accept/SKILL.md` 并按其执行。 | 要汇总交付证据，或有业务判断需要人处理 | 将验收目标与证据、高风险实现、未验证项对应，形成待审或已确认记录 | 不需人工判断时可跳过；未收到反馈保留待判断 |
| `Call the Skill tool with "yanshi-handoff"`。没有 Skill 调用器时，读取同套件的 `../yanshi-handoff/SKILL.md` 并按其执行。 | 换会话、换执行者或上下文不足 | 交接目标、决策、改动、证据、阻塞和下一步 | 同一上下文仍足够则跳过；交接后按约定停下 |
| `Call the Skill tool with "yanshi-retro"`。没有 Skill 调用器时，读取同套件的 `../yanshi-retro/SKILL.md` 并按其执行。 | 有重复 SOP、复发问题或待删约束 | 基于本次证据复盘，提炼可复用动作或删减建议 | 无复盘收益或本次只要交付则跳过 |

子 Skill 缺失、被调用政策阻止或无法加载时，按同行的等效动作完成本步并说明降级；不要求为继续任务补装依赖。

## 下一步选择

先尊重用户限定的任务范围；总控不是发布、改库或扩大修改范围的授权。

1. 有关键契约冲突或未授权副作用时，暂停受影响动作，提出最少的阻塞问题；互不依赖且已获准的工作仍可推进。
2. 当前会话无法可靠继续时按需交接；达到用户约定的预算或停止条件时结束本轮并报告。
3. 有失败时先判断归属：契约不清回对齐；方案不成立回设计；实现问题回实现；工具或环境问题回 E2E 环境准备。只请求验收时返回缺陷，不自行修代码。
4. 没有阻塞时，选择所选路径中最早的真实缺口。常见阅读次序是对齐、设计、拆分、实现、自测、交叉审查、E2E、业务验收；可以跳过，也可以先跑 E2E 为审查提供证据。
5. 当前增量结束但还有增量时继续；本次范围已完成则结束。只有确有价值才进入复盘。

## 证据复用与修复

复用时核对契约、代码版本及未提交改动、环境、数据起点与覆盖范围。发生变化只让受影响结论失效；不能判断影响时标为待重新验证。缺失的证据不是通过证据。

修复后重跑受影响检查，必要时包含交叉审查、E2E 或业务验收。保留原失败及修复后结果，不用重试覆盖历史。已有证据足以支持本次范围时，不为流程完整重新执行。

## 何时停下来问人

目标或预期缺失且会改变验收、材料中存在无法裁定的冲突、需要额外写入或发布授权、必要环境需要人恢复、仍有业务风险需要人判断时，返回：问题、影响、可选处理和建议。

剩余问题不改变方向和验收时，可以记录非阻塞假设继续。连续修复没有新证据或可区分的假设时停止重复尝试；预算只使用已约定的值，不自造全局次数或时限。

## 如何结束

`done` 表示完成本次选用范围；`skipped` 表示未选或已由现有有效结果覆盖；`blocked` 表示缺能力或材料；`waiting-user` 表示需要人的决定。复用时指出对应证据，跳过时不声称执行过。

结尾给出已完成与证据、未完成与原因、是否待人处理。全部状态可直接写在回复里，不强制建立状态文件。E2E 的 case 判定使用它自己的证据模板，不与总控状态混用。
