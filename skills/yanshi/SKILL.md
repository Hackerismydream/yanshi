# 找到下一项缺证据的判断

先读已有需求、CONTEXT.md、变更和运行记录。用一句话说明本次交付目标，以及现在缺的是方案依据、实现、运行证据还是独立审查。用户只请求其中一项时，工作到该项结束。

## 选路

| 当前缺口 | 下一步 | 本步结束的标志 |
|---|---|---|
| 两份需求对预期结果的规定冲突，或缺少决定正确性的业务规则 | 列出冲突条款、受影响目标和需要人决定的问题 | 剩余问题不再改变实现方向和验收结果 |
| 新机制依赖尚未验证的假设，或用户要求攻击方案、做减法、归因优化收益 | 读取 [yanshi-challenge](../yanshi-challenge/SKILL.md) | 关键假设对应反例、证据或最小区分实验 |
| 已有实现，需要实际操作并判断业务目标；或要比较执行组合 | 读取 [yanshi-e2e](../yanshi-e2e/SKILL.md) | 每个目标有契约、运行证据和明确状态 |
| 用户要求另一位审查者检查核心业务路径，或已有发现需要交接修复 | 读取 [yanshi-review](../yanshi-review/SKILL.md) | 审查身份、发现、修复责任和复验结果可追溯 |
| 目标明确，只缺实现 | 使用当前宿主的编码能力；运行项目中已经确认的检查命令 | 变更与实际检查结果对应，业务验收缺口单列 |

读取所选文件及其指向的参考资料，不依赖名为 Skill 的调用工具。若安装中没有该文件，报告具体缺失路径与未执行分支；不自动安装，也不把文件名当作执行成功的证据。完整选路需要安装整个套件。

## 推进与收尾

复杂变更按可独立验收的业务增量推进；只有互不阻塞的增量才分给不同工作树，主 Agent 负责集成。简单任务直接实现和自测。

失败后区分契约冲突、实现偏差与环境阻塞。修复由主实现者完成，随后重新验证受影响的目标；保留原失败记录。只获得验收或审查授权时，返回发现，不自行修代码。

结束时只回答：完成了什么、证据在哪里、哪些目标未验证、什么决定还需要人做。复用旧证据前核对契约、版本、身份与数据起点；不适用或未执行不等于通过。
