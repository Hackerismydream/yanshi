# Agent 开发工作流

> 命名由来：偃师是《列子·汤问》中造出能歌善舞的机关人的工匠，取其“指挥 Agent 干活”之意。（命名说明，非原文内容）

先在第 0 步判断复杂度；简单任务直接实现并自测即可，复杂任务再按需要增加规划、拆分和交叉审查。
把步骤 0–8 当作可裁剪的路径，不要当作逐项强制执行的关卡。
唯一不可让步的原则：端到端测试的预期结果必须来自业务契约，不能把系统返回了什么当作正确答案；工具提供证据，不定义正确答案。
将下文标注“（推断）”的内容视为流程补充，而非来源原文的规则。（推断）

## 何时使用

- 在需要把需求推进到实现、测试和审查时，按本流程组织工作。
- 对简单需求只选实现与自测，不额外增加规划、拆分和交叉审查。
- 对跨模块、状态变化、并发或迁移等问题，考虑增加相应的澄清与验证；不要用固定规模阈值代替判断。（推断）
- 将已有需求材料、现有代码、知识文档和可用测试入口作为上下文。

## 角色

- 用“规划者”负责需求对齐、方案取舍和任务边界。
- 用“实现者”负责实现、自测、集成和修复审查发现的问题。
- 启用交叉审查时，引入其他 Agent 担任“审查者”。
- 无法换 Agent 时，用新会话作为替代，但不等同于其他 Agent 的交叉审查。（推断）
- 按复杂度安排角色；简单任务直接实现并自测。
- 仅将 grill、think、ponytail、handoff、check、implement 视为可选的同类工具示例；没有这些工具时直接执行对应动作。（推断）

## 步骤 0：判断复杂度

- **目的**：为任务选择足够轻的执行路径。
- **输入**：需求描述。
- **动作**：
  - 对简单需求直接实现并自测。
  - 对复杂需求增加规划、拆分和交叉审查。
  - 结合跨模块影响、状态、并发、迁移等风险判断，不凭代码行数决定流程。（推断）
- **输出**：选定本次需要执行的步骤。（推断）
- **何时跳过**：若已有可信的复杂度判断且范围未变，沿用判断，不重复分析。（推断）

## 步骤 1：需求对齐

- **目的**：问清会影响实现方向和验收结果的问题。
- **输入**：需求文档、会议纪要、聊天记录、用户反馈、知识文档与现有代码。
- **动作**：
  - 通过 Grill 式连续追问，与需求提出者多轮对齐目标、范围、边界与关键取舍。
  - 对材料和代码无法回答的问题，向需求提出者或相关人员确认。
  - 当剩余问题已不会显著改变实现方向和验收结果时，结束需求澄清，不预先穷尽实现细节。
- **输出**：澄清后的问题、范围、关键取舍和验收标准，供方案设计使用；在步骤 2 审查后统一沉淀。
- **何时跳过**：目标、边界和验收标准已明确时，复用现有材料。（推断）

## 步骤 2：方案设计与审查

- **目的**：先设计方案，再通过对抗性审查检验核心假设，审查后定稿 Spec 或 CONTEXT.md。
- **输入**：需求澄清结论与相关材料。
- **动作**：
  - 根据需求结论设计方案；怀疑题目本身问错时，用第一性原理重新分析。
  - 对方案做对抗性审查，优先寻找能推翻核心假设的反例；审查不过时，回到方案设计修订。
  - 需要精简方案时，用奥卡姆剃刀删除非必要机制。
- **输出**：将需求对齐与方案审查的结论统一沉淀到 Spec 或 CONTEXT.md，明确问题、范围、关键决策和验收标准，让后续实现和审查的 Agent 共享上下文，不必重读全部对话。
- **何时跳过**：方案沿用成熟模式且没有值得验证的新假设时，直接实现。（推断）

## 步骤 3：拆分与执行

- **目的**：以边界清楚、可独立验收的小范围变更推进需求。
- **输入**：已明确的需求或计划。
- **动作**：
  - 由主 Agent 按复杂度决定执行方式，并负责最终集成。
  - 将复杂需求拆成边界清楚、可独立验收的任务。
  - 只将能独立推进的部分交给其他实现者，在不同工作树中并行开发，最后由主 Agent 集成。
  - 保持每次合并请求的范围足够小。
- **输出**：小范围、可审查的实现变更；按当前任务授权决定是否创建合并请求。（推断）
- **何时跳过**：简单任务跳过拆分和并行，直接实现。已有实现待验证时跳过重复编码。（推断）

## 步骤 4：实现者自测

- **目的**：由实现者先验证实现，再处理不必要的复杂度。
- **输入**：实现变更与相关测试。
- **动作**：
  - 完成与本次实现相关的测试；能通过类型检查、测试和业务断言发现的问题，尽量在开发过程中自行处理。
  - 发现过度设计时清理多余机制。
  - 做了多项优化时，用消融实验判断收益真正来自哪里，去掉贡献很小的复杂度。
- **输出**：测试结果、修复后的实现，以及适用时的消融结论。
- **何时跳过**：已有覆盖当前变更的有效自测结果时，不重复运行相同检查；没有优化归因问题时跳过消融。（推断）

## 步骤 5：交叉对抗性审查

- **目的**：按复杂度引入其他 Agent 的视角检验实现。
- **输入**：需求结论、实现变更与已有测试结果。
- **动作**：
  - 按复杂度引入不同于实现者的其他 Agent 做交叉对抗性审查。
  - 无法换 Agent 时，可用新会话作为替代，但不等同于其他 Agent 的交叉审查。（推断）
  - 将发现的问题统一反馈给主编码 Agent 修复并重新验证。
  - 换会话时交接上下文。
  - 交接需求、关键决策、变更位置、验证结果和未解决问题。（推断）
- **输出**：审查发现、修复情况和重新验证的结果。
- **何时跳过**：任务简单、无需交叉审查时跳过。没有其他 Agent 参与时，说明未做其他 Agent 的交叉审查。（推断）

## 步骤 6：端到端测试

- **目的**：通过真实业务流程验证需求，并取得运行证据。
- **输入**：业务契约、待测实现和可用的端到端环境；环境应支持 Agent 从真实入口执行任务，一直检查到用户需要的结果。
- **动作**：
  - 从业务契约确定预期结果，不从被测系统当前的返回值反推正确答案。
  - 熟悉启动、测试数据准备、版本、账号、权限、清理与重置方法。
  - 通过浏览器、API 或 CLI 执行真实业务流程。
  - 用只读数据库查询确认落库结果，用日志和 Trace 查询链路。
  - 对稳定流程进行脚本化，把入口和排障方法写成 Skill；需要统一入口时封装测试 CLI。
  - 让测试 CLI 按需支持环境检查、数据准备、场景执行、结果查询和清理。
  - 被测产品本身是 Agent 时，同时检查答案质量。
  - 例如，测试创建资源接口时，依据契约核对权限、响应和落库状态，而非直接把首次响应保存为正确答案。（推断）
- **输出**：端到端测试结果，以及支持结论的日志、数据库查询结果或 Trace。端到端测试只覆盖选定环境和场景，生产流量、并发和数据分布仍可能带来新问题。
- **何时跳过**：简单任务可不增加本环节；环境不可用或业务契约缺失时，记录未验证范围，不把其他测试说成端到端通过。（推断）

## 步骤 7：人工 Review

- **目的**：让人工审查聚焦验收目标和业务路径。
- **输入**：验收标准、测试结果、实现变更。
- **动作**：
  - 向人工审查提供材料，先对照验收标准与测试结果，检查测试是否验证了需求真正关心的事情；代码和测试也可能一起误解需求，仍需人给出正确的验收标准。
  - 沿业务路径标出权限、状态变化、并发、重试、数据一致性、迁移和回滚相关实现。
  - 对模式稳定的 CRUD 减少审查投入。
  - 对新增抽象和机制，再用奥卡姆剃刀审查必要性。
  - 提交合并请求时可配合代码审查类工具（如 check）做一轮检查。
  - 合并请求较多时，考虑结合 Git 变更和预设流程使用审查自动化。
  - 在变更范围足够小、完整业务路径逐步得到验证的前提下，不要求人工逐行阅读全部生成代码。
- **输出**：供人工核对的审查清单及已有结论；将等待人工判断的事项与已确认事项分开。（推断）
- **何时跳过**：当前任务不需要人工 Review 时跳过；需要人工判断但尚无反馈时，标明待审，不代替人工给出结论。（推断）

## 步骤 8：沉淀与做减法

- **目的**：复用稳定流程，并删除失去收益的约束。
- **输入**：重复执行的流程、可工具化能力和现有工作约束。
- **动作**：
  - 一个流程重复超过三次，就可以考虑整理成 Skill，之后直接复用。
  - 可以先挑一条平时最常做的自测路径，让 Agent 独立跑通、保留证据，再沉淀有效步骤。
  - 将可工具化的能力做成 MCP 或 CLI，将可复用的流程写成 Skill。
  - 定期复查 AGENTS.md 和 Skill 中的约束，在 Agent 能力变化后重新判断其收益。
  - 把本 Skill 自身也纳入复查，删减不再有收益的约束。
- **输出**：有复用价值时产出工具或 Skill；需要做减法时列出待删约束，不要求每次交付都产生这些产物。（推断）
- **何时跳过**：没有值得复用的流程，也没有待复查的约束时跳过本次沉淀。（推断）

## 5 个思维快捷键 Prompt

按问题选用思考方式，再补充当前任务真正必要的约束。以下 Prompt 均引用原文；Redis、三个优化、OrderService 是原文示例场景，使用时可替换为当前方案或模块。

### 1. 第一性原理

> 不要基于“加 Redis 缓存”这个既定方案继续设计。从第一性原理分析这个接口为什么慢，以及最小必要的解决方案。

适合怀疑“题目本身可能就问错了”的时候。

### 2. 对抗性审查

> 对这个方案做一次对抗性审查，优先寻找能推翻核心假设的反例。

### 3. 消融实验

原文示例中的三个优化是加索引、Redis 缓存和批量查询。

> 给这三个优化设计消融实验，判断真正的收益来自哪里。

### 4. 奥卡姆剃刀

> 用奥卡姆剃刀重新审查这个设计，在满足需求的前提下，删除所有非必要机制。

### 5. 高内聚低耦合

> 按高内聚、低耦合原则审查 OrderService 的职责边界，不要为了拆而拆。

五种认知动作：重新定义问题 → 攻击假设 → 验证贡献 → 删除复杂度 → 整理系统边界。

### 组合版原文

> 从第一性原理重新分析，对当前方案做对抗性审查；核心机制必须通过消融实验验证；方案遵循奥卡姆剃刀，代码保持高内聚、低耦合。

只在适合验证核心机制的任务中选用组合版；其中“必须”属于所引 Prompt，不扩展为整个工作流的强制步骤。（推断）

## 交付物清单

只交付本次选用步骤实际产生的材料，不补造空文档或未执行的结论。（推断）

- 需要需求对齐与方案设计审查时，在审查后定稿 Spec 或 CONTEXT.md，包含问题、范围、关键决策和验收标准。
- 完成实现时，交付小范围变更和自测结果；需要合并请求时沿用当前任务的授权范围。（推断）
- 执行交叉审查时，交付发现、修复与重新验证结果。
- 执行端到端测试时，交付业务契约对应的结果和证据；结论限于选定环境和场景。
- 进入人工 Review 时，交付审查清单及已确认、待确认的结论。（推断）
- 有沉淀价值时，交付可复用流程或工具；有删减价值时，交付约束删减建议。（推断）

## 反模式

- 避免把简单任务套入完整工作流。
- 避免追问不会显著改变实现方向和验收结果的细节，迟迟不开始开发。
- 避免把相互依赖、不能独立验收的工作硬拆成并行任务。
- 避免用系统当前返回值定义端到端测试的预期结果。
- 避免把实现者自己的复查标成独立交叉审查。（推断）
- 避免把工具输出当作正确答案，或把选定环境和场景中的测试通过当作生产行为已得到全面验证。
- 避免同时堆叠多项优化，却不检查收益来自哪里。
- 避免持续增加抽象、Skill 和约束，却不复查它们是否仍有收益。
