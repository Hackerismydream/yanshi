# 想清楚

读 [project-context.md](project-context.md)，说清这次要厘清的一个问题。

1. 结合需求材料、用户反馈、已有 `CONTEXT.md` 和代码，把目标、范围、边界与取舍问清楚。能从材料查到的先查。
2. 剩余问题已经不会显著改变实现方向和验收结果时，结束对齐。成熟的小改动直接给做法。
3. 有实质取舍的方案，优先找能推翻核心假设的反例；机制过多时，在满足需求的前提下删掉非必要的。
4. 简单需求直接给下一步；复杂需求拆成边界清楚、可独立验收的小增量。能独立推进的部分才并行，主 Agent 负责集成。

后续实现者与审查者需要共享上下文时，把问题、范围、关键决策和验收标准写进已有 Spec 或 `CONTEXT.md`。验收标准来自业务规则，不由当前实现倒推。只讨论方案时交付方案即可。
