# 五个思维快捷键

每次选能改变当前决定的动作，不把五项串成固定流程。尖括号内容替换为当前任务。

## 1. 第一性原理：先质疑题目

适用：还未定位原因，就已经决定加缓存、队列或新抽象。

```text
不要基于 <既定方案> 继续设计。从第一性原理分析 <问题为什么发生>，以及最小必要的解决方案。
```

先列出已观察到的现象与约束，再分开可能原因。接口慢时，用现有证据区分查询、网络、序列化、锁等待或重复计算；不能区分就设计观测，不编造瓶颈。交付“原因 → 区分证据 → 最小解决办法”，而不是另一套更大的架构。

## 2. 对抗性审查：找能推翻核心假设的反例

```text
对这个方案做一次对抗性审查，优先寻找能推翻核心假设的反例。
```

先说清方案依赖什么，再找违反条件。若用分布式锁解决重复请求，检查业务真正需要的是互斥还是幂等；锁过期但操作未结束时，原承诺还是否成立？这些是待核实的反例，不是已经发生的事故。

交付反例的前置状态、触发顺序、被违反的业务约束和验证办法。只列“并发风险、性能风险”不构成反例。

## 3. 消融实验：把整体收益拆开

```text
本次叠加了三项优化：<优化一>、<优化二>、<优化三>。
给这三个优化设计消融实验，判断真正的收益来自哪里。
```

固定输入、系统版本、环境与测量口径。比较基线、单项与必要的组合；有交互影响时，不能把某一添加顺序下的差值当成该机制的独立贡献。每个对照写明保留什么、移除什么、观察什么。

交付实际测量或未执行的实验计划，并说明什么结果会使你删除某项优化。样本、重复次数和可接受差异由任务约定，不编造统计显著性。

## 4. 奥卡姆剃刀：删机制，不删需求

```text
用奥卡姆剃刀重新审查这个设计，在满足需求的前提下，删除所有非必要机制。
```

对每个新增机制追问：它保护哪条业务约束？去掉后哪个具体场景会失败？更简单的既有机制能否满足同一约束？证据不足时标待验证，不为减少代码而删除安全或一致性要求。

交付“机制 → 必要约束 → 简化替代 → 验证办法”。效果相近且满足同一约束时，再比较维护复杂度。

## 5. 高内聚、低耦合：按职责切，不按行数切

```text
按高内聚、低耦合原则审查 <目标模块> 的职责边界，不要为了拆而拆。
```

围绕实际修改原因、状态归属与事务边界划分职责。检查拆分是否只是把一次修改散落到更多文件，是否新增循环依赖，是否让同一业务事务更难保持一致。

交付职责归属、需要稳定的接口，以及不应拆开的共同变化部分。没有边界收益时保留原结构。
