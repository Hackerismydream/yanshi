## 最短有效路径

### 什么时候用
用 yanshi 推进一个任务，但不确定要不要先规划。

### 作者原话
> 简单任务直接做，复杂任务再增加规划、拆分和交叉审查。

### 真实例子
待提供：同一类小任务从过重流程改成直接实现的实际记录。

## 想清楚再开工

### 什么时候用

## 写完顺手自测

### 什么时候用
目标已明确，要实现或修复小增量。

### 作者原话
> 能通过类型检查、测试和业务断言发现的问题，尽量让 Agent 在开发过程中自己处理；需要我判断的，则集中到需求有没有理解对、关键业务逻辑是否成立，以及这次改动还有哪些没有验证的风险。

### 为什么（踩过的坑）
原文明确把可自动发现的问题留在开发阶段，把人的精力留给业务判断；没有给出某个具体 Bug 的完整记录。

### 真实例子
待提供：变更、自测失败、修复和重新验证的真实证据。

## 看运行状态再判断

### 什么时候用
已经有错误结果，想定位真实业务路径在哪里偏离。

### 作者原话
> DB 查询用于确认状态，日志和 Trace 用于解释失败，但预期结果仍然必须来自业务契约，不能让 Agent 看到系统返回了什么，就认为什么是正确的。

### 为什么（踩过的坑）
原文指出系统可以返回看似合理、实际不符合需求的结果。这支持运行时取证，不足以支持一个专属的多阶段 debug 方法。

### 真实例子
待提供：最近两周一次完整排障会话；目前不补造复现、根因或修复故事。

## 第一性原理

### 什么时候用

### 作者原话
> 不要基于“加 Redis 缓存”这个既定方案继续设计。从第一性原理分析这个接口为什么慢，以及最小必要的解决方案。

原文用接口慢说明不要未经定位就决定缓存。此处是说明性情境，不是可核实的事故。

## 自然语言 E2E

### 什么时候用
要让 Agent 从真实入口完成最终业务目标，而不是只生成测试代码。

### 作者原话
> 端到端的测试不需要写常规的测试用例，需要定义每个具体的 case 的验收目标

### 为什么（踩过的坑）
作者希望 Agent 感知软件实际运行的状态变化。E2E 帖及评论支持这一目的，不支持普遍禁止所有 AI 测试。

### 真实例子
[原帖](https://x.com/huangtongxueh/status/2109687887264681986)报告过信息查询、多轮交互、状态修改及持久化三类小规模比较；逐 trial 记录、环境与计费依据尚未提供，不能复现或移用它的成绩。待提供一条脱敏可复验路径。
