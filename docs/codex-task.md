# 可直接交给本地 Codex 的任务

你在作者的本地 yanshi 仓库工作。把本次交付包 `yanshi-v1.0` 合入工作分支，并完成能实际执行的检查。目标是作者自用，不做发布宣传，不补造真实案例，不写死模型。

## 输入与范围

输入是本地交付目录或 ZIP，以及当前仓库。先读取交付包 README_CN.md、CHANGELOG.md、design-notes.md、docs/host-validation.md。若交付包尚未放到本机，说明缺失路径；不要从仍是旧版的远端仓库猜出交付内容。

检查 `git status --short`。保留用户未提交改动、项目经验、原图片与许可证。用独立工作分支或 worktree 做本次改造，不覆盖用户正在修改的同名文件。没有明确授权不 commit、push、开 PR、打 tag、发版本，也不更改全局权限与认证配置。

## A. 合入与静态检查

按 skills.json 核对 12 个入口：一个总控、六个日常时刻、五个手动快捷键。v3 的 yanshi-challenge 保留名称但变成小命令；yanshi-e2e / yanshi-review 合入 yanshi-check。先列旧文件处理清单，再清理本仓库已退役的本套件文件；不要误删无关 Skill 或全局目录。

同步 README、README_CN、llms.txt、VERSION、元数据与内部路径。运行：

```bash
python3 scripts/check.py --self-test
```

从新 ZIP 解压到另一个临时目录，再运行同一命令，并核对归档与源目录文件集合和字节一致。保留原始检查输出，不把“准备运行”写成“已运行”。

## B. 机械接入检查

在临时 HOME 中用 setup.py 预览并安装到两个宿主目录；验证目录冲突、悬空符号链接、第二次安装都拒绝覆盖。

在临时项目运行 project 子命令；验证旧 AGENTS / CLAUDE 正文保留，非空 AGENTS.override.md 被正确选中，重复执行不重复插入，已有索引不被覆盖。检查候选规则不自动变 active；脚本安装不代表模型已读到。

## C. 真正启动两个宿主

先记录本机 codex / claude 的版本、登录与当前批准预算；用本机帮助确定可用参数。在独立测试项目安装本地 Skill，保留用户现有工具，不绕过沙箱或审批，不动生产数据。

依 docs/host-validation.md 在 Codex 和 Claude Code 分别做发现、双语路由、小改动、只读审查、手动快捷键、口头 retro、项目写入及新会话读取检查。实际使用的是用户当前选择的配置，不在文件里写模型名。

宿主、凭据、权限或费用授权不足时，完成无收费检查并把对应真实会话标 blocked；不要换别的宿主或模拟模型输出来宣称原宿主通过。

## D. 用真会话完善内容

只从作者提供并授权读取的最近一两周会话抽取实践。每条使用“什么时候用 / 作者原话 / 为什么（踩过的坑） / 真实例子”四项格式。没有原话、没有实际失败或验证的地方留空；不借其他开源项目补作者故事。所有内部信息脱敏，原始凭据不复制。

debug 优先补一条真实翻车。不能只因为文案看起来合理就提升为经验；先保留 candidate，有可核对依据和验证后再设 active。普遍适用的经验只有经作者确认才进入通用 Skill，项目特有内容留在项目。

## 交付

返回实际改动清单、静态与脚本检查输出、两个宿主分别的结果及轨迹路径、未执行项、内容仍缺的真实材料和新 ZIP。更新 verification.md，但不得写不存在的通过率、成本节省或“已经日常用了”的结论。给出建议提交信息，不自行发布。
